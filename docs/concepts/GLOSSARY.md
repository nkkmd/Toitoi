# Toitoi 用語集

**状態: 継続的に更新** | **最終更新: 2026-10-20**

Toitoiでよく使う言葉を、初めて読む方に向けて説明します。実装やAPIに現れる英語の用語を見出しに残し、本文では意味を日本語で説明します。

まず「問い」、Canonical Event、来歴、派生関係、配信方式を押さえると、ほかの文書を読み進めやすくなります。各項目名は仕様の識別子やAPI名を翻訳するものではありません。

[`TOITOI_VOCABULARY.md`](./TOITOI_VOCABULARY.md)は、文脈や関係を表す制御語彙のリストです。この用語集は、プロジェクト全体の概念を説明します。

## Inquiry Model

### Toitoiでいう「問い」

問いは、現場で得られた観察や違和感を出発点とし、未解決の点を保ちながら、他者と共有・翻訳・再解釈できる知識の単位です。

例えば「畑の東側だけ雑草の種類が違う」という観察から、「土壌水分や日照の違いが関係しているのか」という問いが生まれます。別地域の人は、自分の圃場の条件と比較し、新しい観察につなげられます。

### 必要条件

Toitoiの問いとして扱うには、次をすべて満たす必要があります。

- 具体的な観察、違和感、関係のいずれかに由来する。
- 未解決の点が残っている。
- 文脈によって意味が変わる。
- 他者と共有でき、再解釈の余地がある。

### 十分条件

現場経験に根ざし、不確実性を含み、受け手の文脈で捉え直すことができ、比較・関係付け・追加観察につながる対象は、Toitoiの問いとして扱います。

### 問いの核

観察、違和感、関係性、仮説、生態学的な直感、不確実性は、問いを理解する手がかりです。これらは固定のスキーマや必須入力項目ではありません。

### 問いと区別するもの

既知の正解を答える設問、元データそのもの、結論そのもの、作業指示、各配信方式のイベント形式は、それだけでToitoiの問いに当たるわけではありません。

### 用語方針

- `inquiry`: Toitoiの概念や実装・仕様で使う標準用語
- `question`: 一般語としての質問や問い

### 基本思想と役割

問いの共有を通じて、地域固有の条件、土地に根ざした知識、暗黙知、生態系の複雑さを保ちます。他地域への翻訳、追加観察、比較、関係の発見を促すことを重視します。

### 問いの構成要素

| 概念上の要素 | 意味 |
|---|---|
| context | 背景条件 |
| observation | 観察内容 |
| relationship | 関係性 |
| uncertainty | 不確実性 |
| tags | 意味を表すタグ |

この表は概念の整理です。実際のデータ項目・必須条件は、各スキーマと仕様を参照してください。

### Inquiry as Commons

問いは、未解決の点を保ったまま共有され、他者との関係の中で翻訳・再解釈される知識として扱います。

## 主要用語

### inquiry

現場の観察や違和感から生まれ、文脈と不確実性を保ちながら共有する「問い」。実装・仕様で使う標準用語です。

### question

一般語としての「質問」「問い」。概念を厳密に示す場合はinquiryを使います。

### canonical event

通信プロトコルに依存せず意味を表す共通の記録（Canonical Event）。保存・検索・API・AI処理の中心となる正本です。各配信先の記録の単なる写しではありません。

### provenance

問いや観察が、どの出典から、どの文脈で生まれたかを表す来歴情報。生成や取り込みの過程を追跡するために使います。

### lineage

観察や問い同士の派生関係・系譜。「何から派生したか」「何を統合したか」を表し、出典の来歴とは分けて記録します。

### boundary object

異なる地域や立場の人が、それぞれの文脈を保ちながら共有できる対象。Toitoiでは問いを橋渡しに使います。例えば、二つの地域の似た観察を比較しても、土壌や文化の違いまで同一視しません。

### commons

人々が分散的に共有・維持・継承する知識基盤。AI、リレー、索引作成、画面などに加え、知識を共有する仕組み全体を指します。

### relay

イベントを受け取り、配信・保管する中継ノード。Toitoiの初期運用ではNostrリレーを使います。

### indexer

分散した記録を収集し、検索・再構成・表示しやすい形に整理する仕組み。配信方式の差を吸収して、共通の参照形式を組み立てます。

### canonical view

Canonical EventをAPIや画面で参照しやすく整えた形式。元データの全文をそのまま見せず、必要な来歴や派生関係を保持します。

### local AI

利用現場の近くで動くAI。地域の文脈に沿って観察を整理し、必要以上に元データを外へ出さずに処理する設計を目指します。実際のデータ送信範囲は、構成と公開操作によって管理します。

### edge layer

現場側で観察、抽出、署名、送信を担う層。元データを保持し、共有する情報を選ぶ役割を持ちます。

### viewer layer

分散した問いを集め、利用者が参照できる形で返す層。索引作成と画面表示を含みます。

### standard API

配信方式や内部保存形式の違いを吸収し、共通の参照・操作方法を提供するAPI。配信先固有の元イベントではなく、共通の参照形式を返します。

### transport

問いや関連情報を運ぶ通信・保存の仕組み。Nostr、Lingonberry、ATProtoなどを指します。この文書では「配信方式」「配信経路」とも表記します。

### protocol

Toitoiで何を、どの意味・型・機能として扱うかを定める論理的な仕様。意味を扱う仕様と、その運搬を担うtransportを区別します。

### adapter

配信方式固有の入力を、Toitoiの共通表現へつなぐ層。入力検査、署名検証、正規化、重複排除、順序の扱いなどを担当します。

### normalizer

元の記録のばらつきを整理し、扱いやすい形式にそろえる処理。多くはアダプターの内部で行い、正規化だけで意味上の同一性が確定するわけではありません。

### converter

Canonical Eventと各プロトコル固有の表現を変換する層。文字列の符号化・復号だけでなく、意味を保って別の表現へ移す役割です。

### replay

保存済みの記録を、同じ規則で再処理・再構成すること。再索引、検証、履歴の再現に使います。IDを保持するには、保存済みのIDや対応情報も必要です。

### storage snapshot

保存状態をまとめて参照できる形式。APIや索引作成の入力に使い、元データ、Canonical Event、取り込みログなどを含む場合があります。

### append-only

既存の記録を上書きせず、新しい記録を追加して履歴を残す方針。訂正は新しいイベントと派生関係で表します。

### derived index

保存されたCanonical Eventから作る、検索・参照用の補助索引。正本ではなく、再構築可能な派生データです。

### capability

プロトコルや保存機能が対応する処理を示す性質。再処理できるか、元データへの参照を持つか、などを記述します。

### registry

プロトコル記述子を登録し、一覧・参照できるようにする仕組み。利用可能な方式の選択や、重複登録の防止に使います。

### descriptor

名前、対応機能、来歴情報の扱いなどをまとめた記述子。実装自体ではなく、実装を比較・列挙・選択するためのメタデータです。

### canonical semantics

配信方式や保存形式に依存しない、Toitoiの記録が表す意味。索引作成や変換で、その意味を変えないことを重視します。

### semantic layer

形式の違いよりも、記録が何を表すかを扱う層。Canonical Eventや問いの意味を整理する際に使う言葉です。

### rawRef

別に保存された元イベントやデータ本体への参照。再取得、再処理、監査、復旧に使い、sourceId、relay、storageId、payloadHashなどを持ち得ます。

### provenance summary

APIや画面で扱いやすくまとめた来歴の要約。sourceCountやsourceProtocolsなどを含み、全履歴を置き換えるものではありません。

### identity mapping

元の記録の識別子とCanonical IDの明示的な対応付け。内容の類似だけで統合せず、同一性の根拠がある場合に使います。

### identity key

Canonical Eventの意味上の安定した内容から、同じ規則で再計算できる照合キー。来歴やrawRefからは計算せず、Canonical IDそのものとも区別します。

### identity claim

照合キーとCanonical IDの対応を示す検証可能な申告。第三者による検証のため、JSONで保持し、署名や検証方式を差し替えられるようにします。

### multi-transport

複数の配信方式をまたいで、共通のCanonical Eventの参照形式を扱うこと。複数経路からの取り込みと、複数経路への配信の両方を含みます。

### fan-in

複数の配信経路や出典の記録を、共通の参照形式に集約すること。集約して表示することと、同一性を統合することは区別します。

### fan-out

一つのCanonical Eventを、複数の配信先向けの表現へ変換して送ること。

### local-first

まず現場で観察・処理し、必要な情報を選んで共有する考え方。現場側の設計方針です。

### tacit knowledge

言語化しにくく、経験や身体的な実践に根ざした知識。日本語では「暗黙知」と呼びます。

### commons memory

知識を共有する人々が、共同で保持・継承する知識生成の記録。来歴情報が持つ社会的な役割を表します。

### TIP

Toitoi Improvement Proposalの略。語彙や共有仕様の変更を提案し、互換性や影響を検討するための提案形式です。

### provenancePolicy

来歴情報の保存・要約・APIでの扱いを示す方針。プロトコルごとの違いを表すメタデータです。

### capability matrix

複数のプロトコルの対応機能を比較する表。登録簿やAPIの機能照会で使います。

### metadata-only protocol

実データの再処理よりも、メタデータの取り扱いを中心とする方式。localfsのように、保存機能が限定された実装で使われます。

### projection

内部の記録を、外部や別の層で扱いやすい形へ写すこと。配信方式ごとの表現や、API・画面向けの派生表現を作る処理を指します。

## 使い分けの目安

| 確かめたいこと | 主な用語 |
|---|---|
| どの問い・観察を表すか | inquiry、Canonical Event |
| 同じ記録か | canonical identity、identity mapping |
| どこから来たか | provenance、rawRef |
| 何から派生したか | lineage |
| 何に関連しそうか | 文脈や内容の類似性。同一性とは別に扱う |
| どう運ぶか | transport、relay、fan-in、fan-out |
| どう探し、表示するか | indexer、derived index、canonical view |
